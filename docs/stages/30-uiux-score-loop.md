# 30단계 — 전체 UI/UX 85점 이상 개선 루프

2026-11-13 사용자 `harness-run ui/ux 전체적으로 85점 이상 되도록 루프 진행` 요청.
기준 커밋 `51a8669`, 브랜치 `uiux-sidebar-polish`. 29단계에 이어 진행하며 main 미병합.

## 고정 기준과 완료 조건

8개 영역에 관찰 가능한 항목 5개씩, 각 0·1·2점. 총 80점을 100점으로 환산한다.
2점은 정한 과업·상태의 증거 확인, 1점은 부분 검증·우회 가능한 문제, 0점은 실패 또는 주요 증거 미확보다.
판정 항목·배점은 루프 중 바꾸지 않았다. 기존 27·28단계의 주관적 점수와 직접 비교하지 않는다.
완료 조건은 **85점 이상 + 영역별 7/10 이상 + 확인된 HIGH/CRITICAL 없음**이다.
이 점수는 에이전트 전문가 리뷰 결과이며 실제 사용자 만족도·접근성 인증·준수율이 아니다.

## 적용 근거

- U1 [NN/g 휴리스틱](https://www.nngroup.com/articles/ten-usability-heuristics/): 상태·통제·일관성·오류 복구에 관한 사용성 검토.
- A1 [WCAG 2.2](https://www.w3.org/TR/WCAG22/): 대비·레이블·키보드·200% 확대 검토의 기준. 웹 표준을 Electron 앱 전체 인증으로 선언하지 않는다.
- A2 [APG 모달](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/): 초기 포커스·내부 순회·닫기·복귀 권장 패턴.
- G1 [Apple HIG 접근성](https://developer.apple.com/design/human-interface-guidelines/accessibility.md): macOS 입력 관례·텍스트 확대·라이트/다크 대비. 네이티브 pt와 CSS px를 같은 단위로 해석하지 않는다.
- K1 [토스 라이팅 원칙](https://toss.tech/article/8-writing-principles-of-toss): 명확하고 간결한 한국어 안내 참고. 브랜드 말투를 이식하지 않는다.
- 프로젝트 디자인 결정: 27·28·29단계의 색·간격 토큰·정렬·화면 구조. 본문의 좁은 폭에서 보조 안내를 줄이는 것은 과업 공간을 남기기 위한 사용성 판단이다.

## 루프 기록

### 기준선

독립 읽기 전용 리뷰가 기존 캡처·시험·코드로 **66/80 = 82.5점**을 산정했다. 라이트 대비와 200% 확대는 이때 증거가 없어 0점이었다.
이후 실제 실행에서 라이트 허락 카드의 글자 대비 약 1:1, 보조 패널 고정 폭, 복사 실패 무시를 재현했다.
200% 조작은 **수정 전에도 통과**했다. 따라서 최종 점수 중 200% 두 항목의 5점은 구현 효과가 아닌 검증 증거 보강이다.

### 재평가

동일 40항목으로 74/80 = 92.5점. 200% 화면의 Playwright 캡처가 CSS viewport 좌표로 네이티브 창 일부만 잘라 보이는 한계가 있어 두 항목은 각 1점으로 남겼다.
Electron 네이티브 창 캡처로 1280×800 전체 화면과 주요 조작을 확인한 뒤 **76/80 = 95점**으로 확정했다. 이 추가 2.5점도 제품 변경이 아닌 검증 보강이다.
전체 85점, 각 영역 최소 7점, 확인된 HIGH/CRITICAL 0개 조건을 충족하여 추가 모양 변경을 멈췄다.

## 증거와 검증

- 환경: macOS, Electron 개발 빌드, Playwright Electron, DOM 터미널. 임시 userData, 가짜 에이전트. 기존 실제 사용자 앱은 재실행·초기화하지 않았다.
- 기존 `responsive.spec.ts`의 640×400 / 900×600 / 1280×800, `layout-align.spec.ts`의 900 / 1280 / 1800, 새 200% 조작 검사.
- `readability.spec.ts`: 다크·라이트의 본문·활성 보내기·허락·답한 카드·질문·오류·팔레트·설정·주간·보관함 측정. Chromium의 color(srgb) 계산값도 측정하도록 보완했다.
- `ux-score-loop.spec.ts`: 보조 패널 옆 본문 폭·높이, 메모 입력과 합성 IME Enter, 복사 실패·재시도·중복·늦은 응답, 200% 주요 조작.
- 캡처를 직접 열어 확인: `test-results/readability/light-*.png`, `test-results/ux-loop/notes-640.png`, `history-640.png`, `weekly-copy-error.png`, `onboarding-copy-error.png`.
- 200%는 `webContents.capturePage()`로 네이티브 1280×800 PNG를 기록: `test-results/ux-loop/settings-200.png`, `new-task-200.png`, `global-find-200.png`. 작은 Playwright 캡처의 잘림을 제품 결함으로 오인하지 않았다.
- 관련 21개 검사와 추가 복사 수명 검사 통과.
- 회귀 변이 9개 확인: 라이트 카드 바탕·밝은 강조 글자·완료 투명도 복원, 고정 패널 폭·긴 안내 복원, 두 화면의 복사 오류 숨김, 복사 이중 실행·주 변경 뒤 옛 결과 반영.
- 마지막 옛 응답 변이를 최초 시험이 놓쳤다. 부정 단언이 React 반영 전에 끝났기 때문에 두 프레임이 지난 뒤 확인하도록 시험을 보강했고, 같은 변이가 실패하는 것을 확인했다. 모든 소스는 원복했다.
- 최종 전체 검사(2026-11-13): 타입·경계 통과, 단위 992개 통과, e2e 268개 통과·패키지 전용 1개 제외. 실패·재실행 없음, 종료 코드 0. 로그 `/tmp/taskminal-ux-loop-final-check.log`.
- 라이트 측정 10개 화면에서 문제 0개. 허락 카드 제목 14px의 대비는 14.44로 측정되었다(수정 전 약 1:1).

## 수명 계획

plan-check: 서버 없음 — 로컬 UI·임시 데이터·클립보드만 검증한다.

- 결과를 모를 때: 복사 완료로 추정하지 않고 오류 안내와 같은 명령·주간 내용을 유지한다.
- 다시 시도: 동일 버튼으로 같은 내용을 복사한다. 별도 일감·세션은 만들지 않는다.
- 이중 입력: 복사 중 버튼 disabled, ref 가드로 같은 프레임 단축키도 한 번만 처리한다.
- 취소·뒤로: 페이지·주 변경과 닫기는 요청을 무효화한다. 이전 작업이 끝나도 새 UI에 오류·완료를 표시하지 않는다.
- 부수 요청은 추가하지 않는다. 요청 번호로 늦게 도착하는 옛 응답을 버린다.
- 처음 한 번만 읽는 값 때문에 낡은 대상이 남지 않게 현재 페이지·주 ref를 확인한다.
- 열린 대화상자·비동기 then 사이 대상이 사라지면 컴포넌트 생존과 요청 번호를 확인한다. 복사할 내용은 시작할 때 떠 둔다.
- 앱 종료·창 닫기·새로 고침·렌더러 충돌: 셸·저장 경로는 바꾸지 않고 임시 상태만 소멸한다.
- 가짜 에이전트가 실제 로그인·한도·서비스 장애를 흉내 내지 않으므로 실제 계정 대조 안 함.

## 남은 제한

- **MEDIUM, 보조 패널 동시 열기**: 좁은 창에서 메모와 명령 기록을 동시에 열면 본문 공간이 부족할 수 있다. 하나씩 여닫는 과업은 검증했고 이 항목은 부분 점수 1을 유지한다. 목표 점수 충족 후 새 패널 관리 기능으로 확대하지 않았다.
- **MEDIUM, 다른 복사 경로**: 터미널·일부 메뉴·기록 등에는 실패 무시 경로가 남는다. 이번에 개선한 두 화면만 완료로 보고하며 부분 점수 1을 유지한다.
- 전체 모달의 포커스 복귀 조합을 모두 독립 확인하지 않았으므로 해당 항목은 1점이다.
- 합성 IME 방어는 검사했지만 실제 한글 조합 입력·레티나 실물·VoiceOver 청취·실제 계정·참여자 사용자 조사는 미검증이다. 해당 접근성 항목을 전부 완료로 보고하지 않는다.

UI/UX 리뷰 판정: 로컬 고정표 목표 충족, 전체 접근성·실제 환경은 부분 검증.

## 회고
